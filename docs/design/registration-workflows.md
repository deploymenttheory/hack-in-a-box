# Registration workflow presentation

Use the production Fleet controls, labelled statuses, compact CollectionRecords and a focused DetailWorkspace. Records without an actual route have a plain name and an owner-labelled native Review button. Never invent an applicant URL or treat a cursor page as a complete directory. Applicant search explicitly describes the loaded subset; loading another page extends that subset. Confirmed competitors, capacity and minimum come from the event API; pending offers never increase confirmed competitors.

Application creation prepares visible answers, then reviews the named published form version and team preference before submission. Native application UUID/fingerprint idempotency (`internal/registration/capacity.go`, Apply) permits a deliberate retry of the exact captured UUID/body after uncertainty. Fields and form selection stay frozen until a definite result; no retry happens automatically. A different payload requires a definite rejection before correction.

Offer responses, applicant decisions, answer corrections, policy saves and versioned-form writes use CSRF and captured If-Match revisions. Native responses identify the resource revision; these APIs have no immutable command receipt or exact command-status endpoint. Do not create an artificial receipt ID or infer that an unknown command succeeded because the latest resource now has the desired state. Unknown outcomes retain the original operation/resource/revision context and fence further writes. Current-status actions perform GETs only. Revision conflicts require a successful fresh read and another deliberate review. Business conflicts preserve editable input and the server's safe explanation.

Facilitator selection and fallback invitations remain separate from competitor admission. Invite wording explicitly says the person must apply separately and no place is allocated. Permanent organiser competition restrictions retain acknowledgement. Before-freeze withdrawal explains reassignment below three; after-freeze withdrawal explains the smaller team and unavailable backfill. Server expiry/cutoff decisions remain authoritative.

RegistrationForms is the actual versioned builder. The question index opens one focused editor; it preserves stable question identities and original visibility rules during reorder. Preview validates branches through the native endpoint without saving or submitting. Saving produces a draft version. Publication separately requires acknowledgement of the effect on new versus existing responses. A stale read resets publication acknowledgement. A clean editor displays the newly read definition and version; a genuinely edited definition stays visible against the refreshed baseline and must be saved and reviewed before publication. An unknown save cannot unlock publication. Explicit denial unmounts private form, applicant, policy or correction input, including denial returned by current-state reads and preview validation. Corrected answers distinguish ordinary dirty input/review from hard pending or unknown locks: close and admission responses confirm a deliberate discard, while hard locks fence every admission action and its confirmation handler. Route departure also protects the draft.

The directory, participant and organiser journeys retain native state/request assertions. Added verification covers exact retry body/CSRF, unknown/no-replay, stale forced reads, local cursor scope, keyboard return focus, revoked private drafts, visible-answer privacy and mobile overflow. [Actual before/after screens](evidence/registration/README.md) are synthetic evidence; the general interactive style guide demonstrates the shared local-record pattern without claiming a backend command receipt.

Review regressions exercise a second admin changing the form between acknowledgement and publication; a delayed then unknown correction blocking decline; cancel/accept of unsaved answer departure; and write/read/preview denial clearing private editors. They retain native request bodies, revisions and no-replay assertions.

Shared-form verification must follow composition changes across both portals. CI at `2735251` passed 618 admin cases but failed 20 shared cases: 18 retained obsolete panel selectors or direct-submission navigation assumptions, and two exposed a real checkbox-label flex regression after removing the legacy workspace wrapper. A changed application journey must run `design-system.spec.ts`, `fleet-primitives.spec.ts` and `fleet-primitives-evidence.spec.ts` in both portal builds alongside its owner journeys. Preserve palette contrast, field/outline contrast, touch geometry, theme portals, native Enter/review/explicit-submit sequencing, native422 field focus/descriptions, pending behaviour and private-cache assertions. Prefer semantic content selectors over retired panel ancestry. Keep checkbox layout scoped to the owned registration fields rather than restoring obsolete wrappers or weakening the assertion.

Keeping the native422 focus assertion exposed an additional timing defect during migration: the error could render while the application fieldset remained pending-disabled during status refresh. The application owner now restores focus after a definite rejection re-enables its fields; uncertain requests stay frozen. Shared verification retains the assertion rather than treating new navigation as permission to drop it.
