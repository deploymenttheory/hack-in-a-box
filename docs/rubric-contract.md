# Versioned common rubric

Rubric configuration is separate from scores. Organisers save immutable definitions, approve an exact version and reference its ID, version and public digest in the common challenge document. Templates supply five equally weighted 1–10 categories and descriptive anchors for both supported modes. Cloned defaults remain unapproved drafts; viewing them neither creates a rubric version nor changes the template clone. A legacy template without a mode requires explicit organiser review before approval.

The native challenge approval requires the exact approved reference. The guarded common challenge release publishes that snapshot in the same PostgreSQL transaction at T−7 calendar days; missing, stale, substituted or unapproved references fail closed. The attendee endpoint derives access from the actually released challenge and current confirmed competition status. It cannot publish a rubric early. Every confirmed attendee receives the same public definition. Private judge guidance is a separate organiser configuration field and never enters the public digest or projection.

After publication, a new definition requires approval, an impact review and a reviewed notice. Publication retains the notice and affected confirmed recipients atomically with the new challenge/rubric version. The notice is available with the common published rubric; channel delivery belongs to the communications providers and reviewed campaign orchestration. A failed notice write rolls back publication. Organisers can read exact historical definitions and paginated version/restart decisions. Historical definitions never silently replace a challenge's exact reference.

## Assessment consumers

`rubric.Service.StartAssessmentInTransaction` supplies the consuming contract for checkpoint and final-assessment owners. Call it inside the same transaction as the consumer's immutable assessment write. Retain its run ID, exact rubric reference, purpose and frozen submission revision alongside that write. A failed outer transaction must roll back the first-use freeze too. Do not take a definition from the organiser editor or a separately cached latest version.

The contract rechecks the current published team, resource assignment/conflicts, actual live clock, current event stage and common challenge publication. Checkpoints require current mentor/reviewer authority during live work before cutoff. Final assessment requires elapsed cutoff and a frozen final submission. Judges must have current assignment and the configured number of conflict-free required judges must be available. Qualification mode's judged final additionally requires the finalist owner to inject its current recorded selection policy; an absent policy fails closed. No mentor scores or ranks enter this fresh judged-final contract.

An assessment run retains its original immutable rubric version. First committed use freezes it; later criteria changes cannot reinterpret existing records. Publishing a changed version after use requires an explicit restart that supersedes the previous run while retaining its identity and history. A consumer cannot use a superseded run or silently bind an old run to a new publication. All-team category and overall award consumers must use the same moderated `judge_final` run. Disbanded teams cannot start an assessment.

This contract creates no scores, moderation decisions, rankings, finalist selections or awards. Those consuming implementations own averaging each category across required judges and summing the categories, with the recorded tie and release policies. Optional side quests carry evidence guidance only; their schema has no bonus-points field.
